PVE-UPS — Benutzerhandbuch

Eine schlanke USV-Shutdown-Appliance für Proxmox VE: Sie überwacht eine oder mehrere USVs — per SNMP oder über einen NUT-Server — und fährt bei Stromausfall die zugeordneten Proxmox-Hosts geordnet herunter, ohne irgendwo von Hand gepflegte Konfigurationsdateien. Dieses Handbuch richtet sich an technisch versierte Administratoren, die das Produkt noch nicht kennen.

1 Was ist PVE-UPS?

PVE-UPS ersetzt klassische, herstellergebundene USV-Shutdown-Appliances (wie APC PowerChute Network Shutdown) für Proxmox-Umgebungen. Die Software läuft als ein einzelner, ressourcenschonender unprivileged LXC (~256 MB RAM) und benötigt nur ein Installer-Skript.

Kernfunktionen

  • Überwachung einer oder mehrerer USVs — mit SNMP-Netzwerkkarte (Standard RFC 1628 oder Hersteller-MIB: APC PowerNet, CyberPower, SNMP v1/v2c/v3, reine Python-Implementierung) oder über einen NUT-Server, worüber USB- und seriell angeschlossene USVs gelesen werden.
  • Geordneter Shutdown der Hosts über ein Proxmox API-Token — kein Root-SSH nötig. Ziel können Proxmox-VE-Knoten (Recht Sys.PowerMgmt) oder ein Proxmox Backup Server (Sys.PowerManagement) sein, je Host wählbar.
  • Host↔USV-Zuordnung mit Logik pro Host (UND/ODER) für redundante Netzteile bzw. aufgeteilte Last, inkl. Schaubild im Webinterface.
  • Komplette Einrichtung über einen Web-Wizard mit Test-Buttons.
  • Weboberfläche auf Englisch und Deutsch — automatisch passend zur Browsersprache.
  • Fail-safe: ein Kontaktverlust zur USV löst standardmäßig nur Alarm aus, keinen Shutdown.
  • Dry-Run-Modus für eine gefahrlose Inbetriebnahme.
  • Lesender REST/JSON-Status für Monitoring (/api/status, /api/health).

2 Voraussetzungen

  • Ein Proxmox VE-Host, auf dem der LXC laufen kann. Typischerweise einer der zu schützenden Hosts. Standalone-Hosts und Knoten eines Clusters funktionieren gleichermaßen als Ziel — jeder Host wird einzeln über seine eigene API heruntergefahren, und PVE-UPS fasst weder HA-Manager noch Quorum an.
  • Eine oder mehrere USVs, auf eine von zwei Arten erreichbar:
    • mit SNMP-Netzwerkkarte, die die Standard-RFC-1628-UPS-MIB (herstellerunabhängig) oder eine unterstützte Hersteller-MIB bereitstellt — APC PowerNet oder CyberPower, womit auch Karten ohne RFC 1628 erfasst sind (siehe Abschnitt 5), oder
    • per USB- oder seriellem Kabel an einer Maschine, auf der ein NUT-Server (upsd) läuft — siehe Abschnitt 5.
  • Netzwerkverbindung zwischen Appliance und USV-Quelle (Lesezugriff genügt: UDP 161 bei SNMP, TCP 3493 bei NUT) sowie zur API der zu schützenden Ziele (HTTPS, Port 8006 bei Proxmox VE, 8007 beim Proxmox Backup Server).

Neben Proxmox-VE-Knoten lässt sich auch ein Proxmox Backup Server herunterfahren — jeder Host-Eintrag hat dafür einen Typ. Die beiden unterscheiden sich nur darin, wie sie angesprochen werden; alles Weitere (USV-Zuordnung, UND/ODER-Logik, Reihenfolge, Schwellen) gilt für beide gleich. Siehe Abschnitt 4.

PVE-UPS gehört in ein internes (Management-)Netz. Die Appliance hält API-Token, mit denen sich Server ausschalten lassen — sie ist also wie jedes andere Management-Werkzeug zu behandeln: nur aus vertrauenswürdigen Netzen erreichbar, niemals ins Internet exponiert, und hinter derselben Firewallierung, Segmentierung und Zugriffskontrolle wie die Proxmox-Weboberflächen selbst. Das Webinterface ist passwortgeschützt, /api/status und /api/health sind aber bewusst ohne Anmeldung lesbar, damit ein Monitoring sie abfragen kann — auch deshalb sollte die Appliance nicht öffentlich erreichbar sein.

3 Installation & Einrichtung

Die Installation erfolgt direkt aus der Proxmox-Node-Shell (Webinterface → Node → >_ Shell, als root). Das Skript lädt das aktuelle Release-Paket von GitHub nach, entpackt es und legt den LXC an:

bash -c "$(curl -fsSL https://github.com/ffind-dev/pve-ups/releases/latest/download/install.sh)"
# z.B. mit fester IP:
curl -fsSL https://github.com/ffind-dev/pve-ups/releases/latest/download/install.sh | bash -s -- \
  --ctid 950 --ip 10.0.0.50/24 --gateway 10.0.0.1 --hostname pve-usv

Alle Optionen sind optional; --help listet sie mit ihren Standardwerten (als Einzeiler: … | bash -s -- --help).

--template-storage <name>local Storage, auf den das Debian-12-Template geladen wird (Inhalt vztmpl). Der Standard weicht auf einen anderen geeigneten Storage aus; ein ausdrücklich genannter wird abgelehnt, wenn er keine Templates aufnehmen kann

PVE-UPS ist außerdem auf community-scripts.org gelistet (dort nach „PVE-UPS" suchen), einer community-gepflegten Sammlung von Proxmox-Helper-Skripten. Der Einzeiler oben bleibt der Referenzweg.

Anschließend das Webinterface unter http://<container-ip>:8080 öffnen und den Wizard durchlaufen:

  1. UI-Passwort setzen.
  2. USVs anlegen (Quelle, Adresse, Zugangsdaten — siehe Abschnitt 5) und je USV mit „USV testen" prüfen.
  3. Hosts eintragen: je Eintrag den Typ wählen (Proxmox VE oder Proxmox Backup Server), das zugehörige API-Token hinterlegen (siehe Abschnitt 4) und „Verbindung testen". Festlegen, welche USVs einen Host versorgen und nach welcher Logik (UND/ODER).
  4. Schwellwerte setzen bzw. die Standardwerte übernehmen.
  5. Optional den Benachrichtigungs-Webhook einrichten (HTTP-POST an ein Ticket-/Chat-/Monitoring-System): Format und Stufe wählen, anschließend mit „Testbenachrichtigung senden" prüfen — siehe Webhook-Benachrichtigungen.
Solange der Dry-Run aktiv ist, wird nichts heruntergefahren — ideal zum Testen. Erst wenn alles passt, den Dry-Run deaktivieren (Modus „SCHARF").
Läuft der LXC auf einem der geschützten Hosts, diesen in der Host-Liste als „Dieser Host" markieren — er wird dann garantiert zuletzt heruntergefahren.

4 API-Token anlegen

Jeder Host-Eintrag authentifiziert sich mit einem API-Token — jederzeit widerrufbar und ein Ersatz für den Root-SSH-Zugang. Welches Token anzulegen ist, hängt vom Typ des Eintrags ab, denn Proxmox VE und Proxmox Backup Server nutzen unterschiedliche Token-Schemata und unterschiedliche Rechtenamen:

Proxmox VEProxmox Backup Server
API-Port80068007
RechtSys.PowerMgmt Sys.PowerManagement
Vergeben auf/nodes /system/status
Feld „Node"der echte Node-Name freie Bezeichnung (PBS ignoriert es)
Der falsch gewählte Typ ist die häufigste Ursache für einen fehlschlagenden Test: ein als „Proxmox VE" eingetragener Backup Server weist die Anfrage rundweg ab und meldet „Authentication failed (token invalid?)" — auch wenn das Token selbst völlig in Ordnung ist.

Proxmox VE

Einen dedizierten Benutzer mit ausschließlich dem Power-Recht und einen API-Token erzeugen — einmalig, in der Shell eines beliebigen Proxmox-Knotens:

pveum user add ups@pve
pveum role add UpsShutdown -privs "Sys.PowerMgmt"
pveum acl modify /nodes -user ups@pve -role UpsShutdown
pveum user token add ups@pve shutdown --privsep 0

Der letzte Befehl gibt Token-ID (ups@pve!shutdown) und Secret aus. Beides im Wizard eintragen und mit „Test" prüfen.

Im Cluster werden die Befehle nur einmal ausgeführt. Benutzer, API-Token und ACLs liegen auf Datacenter-Ebene (/etc/pve) und gelten damit auf jedem Knoten — bei jedem Knoten dieselbe Token-ID und dasselbe Secret eintragen. Nur Standalone-Hosts ohne gemeinsamen Cluster brauchen jeweils einen eigenen Benutzer samt Token.

Jedem Host-Eintrag seine eigene API-URL geben (https://<ip-dieses-knotens>:8006). Die Proxmox-API würde eine Anfrage zwar an einen anderen Knoten weiterreichen, aber ein bereits heruntergefahrener Knoten kann das für die nachfolgenden nicht mehr tun.

Jedem Host-Eintrag seine eigene API-URL geben — sie entscheidet, wo der Shutdown landet. PVE-USV spricht den Knoten hinter der eingetragenen URL direkt an (/nodes/localhost/status); heruntergefahren wird also die Maschine, die antwortet. Proxmox behandelt diese Form lokal, statt den Knoten über den Cluster aufzulösen — genau richtig, während Knoten wegbrechen und das Quorum wackelt. Die Folge: Ein vertippter „Node“ kann den Shutdown nicht mehr fehlleiten — zwei Einträge mit derselben URL aber schon, weshalb PVE-USV davor sowohl beim Bearbeiten als auch im Selbsttest warnt.
Geprüft wird „Node“ trotzdem — er beschriftet alles andere. Der Name benennt den Host im Dashboard und in jedem Ereignis; passt er zu keinem Knoten, ist all das irreführend. „Testen“ vergleicht ihn mit der Knotenliste der API, bietet den passenden per Klick zur Übernahme an und füllt ein leeres Feld. Es gelten die Regeln von Proxmox: nur Buchstaben, Ziffern und - — keine Punkte, ein FQDN wie pve01.example.com wird also rundheraus abgelehnt — und Groß-/Kleinschreibung zählt, PVE01 ist nicht pve01. Teilen sich Einträge eine API-URL, wandert der Name zurück in den Shutdown-Pfad; eine Abweichung gilt dann als Fehler statt als Warnung.

Proxmox Backup Server

Diese Befehle in der Shell des Backup Servers ausführen. Zu beachten: die ACL wird zweimal vergeben — einmal an den Benutzer, einmal an das Token:

proxmox-backup-manager user create ups@pbs
proxmox-backup-manager user generate-token ups@pbs shutdown
proxmox-backup-manager acl update /system/status Admin --auth-id 'ups@pbs'
proxmox-backup-manager acl update /system/status Admin --auth-id 'ups@pbs!shutdown'

generate-token gibt Token-ID (ups@pbs!shutdown) und Secret aus — das Secret wird nur ein einziges Mal angezeigt und lässt sich nachträglich nicht wieder abrufen. Als API-URL https://<pbs-ip>:8007 eintragen und mit „Test" prüfen.

Drei Details unterscheiden sich von Proxmox VE und erklären die Befehle oben:

  • Beide Einträge sind nötig. Auf PBS werden die Rechte eines Tokens aus dessen eigenen ACL-Einträgen berechnet und anschließend mit denen seines Benutzers geschnitten — ein Token kann seinen Benutzer also nie übersteigen. Fehlt einer der beiden Einträge, hat das Token das Recht nicht.
  • Die Rolle ist Admin. PBS kennt keine feingranulare Power-Rolle — Sys.PowerManagement trägt nur Admin. Die Vergabe auf /system/status statt auf / hält den Umfang so eng, wie PBS es zulässt.
  • Das Feld „Node" ist nur eine Bezeichnung. PBS ignoriert den Node im API-Pfad, der Shutdown geht immer an /nodes/localhost/status. Der Eintrag darf also heißen, was im Dashboard gut lesbar ist; nichts muss zum Hostnamen passen.
Gut abwägen, ob ein Backup Server hier überhaupt eingebunden werden soll. Das obige Token ist ein Admin-Token, und PVE-UPS muss die PBS-API aus genau der Umgebung heraus erreichen, die es schützt. Diese Kombination verbreitert den Weg von einem kompromittierten Virtualisierungshost zu den Backups — also zu dem, was eine solche Kompromittierung gerade überleben soll. Für Produktivumgebungen empfehlen wir daher, PBS nicht an dieselbe PVE-UPS-Instanz zu hängen, die die PVE-Hosts verwaltet. Alternativen: dem Backup Server einen eigenen USV-Shutdown-Weg geben (eigene PVE-UPS-Instanz, nur aus einem getrennten Management-Segment erreichbar) oder ihn kurze Ausfälle auf seiner eigenen USV-Laufzeit aussitzen lassen.

5 USV-Quellen

Jeder USV-Eintrag im Wizard hat eine Auswahl „Gelesen über". Beide Quellen lassen sich in einer Instanz frei mischen, und alles Weitere — Schwellwerte, Host-Zuordnung, Fail-safe-Regeln — ist für beide identisch.

SNMP (USV mit Netzwerkkarte)

In der Weboberfläche der USV-Netzwerkkarte (meist unter Network → SNMPv1 bzw. SNMPv3) den Zugriff aktivieren und der Appliance-IP Lesezugriff geben. Es wird nie etwas geschrieben. Standardport 161/UDP.

Welche MIB gelesen wird

Jede SNMP-USV hat eine Einstellung MIB. Sie entscheidet, welcher Satz an Objekten abgefragt wird — die Werte selbst, die Schwellwerte und alles Weitere sind in beiden Fällen dieselben.

  • Automatisch (Standard und für nahezu jedes Gerät die richtige Antwort): Es wird der Standard RFC 1628 gelesen und auf eine Hersteller-MIB gewechselt, sobald die USV darauf antwortet. Die Erkennung kostet keine zusätzliche Abfrage, und ein späteres Firmware-Update, das RFC 1628 nachrüstet, wird von selbst übernommen.
  • RFC 1628 (Standard): die herstellerunabhängige UPS-MIB, sonst nichts.
  • APC PowerNet: die MIB der Netzwerkkarten von APC/Schneider.
  • CyberPower: die CPS-MIB der CyberPower-Netzwerkkarten (RMCARD-Familie). Sie wird Wert für Wert abgefragt — siehe unten.

Besonders bei APC ist eine Hersteller-MIB nötig: Schneider unterstützt RFC 1628 nur auf der Network Management Card 2 (AP9630/AP9631/AP9635) ab Firmware sumx/sy v5.1.7; die älteren NMC1-Karten (AP9617/AP9618/AP9619) sprechen ausschließlich PowerNet und sind über den Standard gar nicht lesbar. Auch auf Karten, die beides beherrschen, ist PowerNet die bessere Quelle: Sie liefert die Restlaufzeit in Hundertstelsekunden statt in ganzen Minuten und meldet einen Selbsttest als eigenen Zustand — RFC 1628 kann einen Selbsttest nicht von einem echten Stromausfall unterscheiden.

CyberPower-Karten beherrschen meist auch RFC 1628, aber nicht alle, und manche Firmware beantwortet keine Anfrage nach mehreren Werten auf einmal — nicht mit einem Fehler, die Anfrage läuft schlicht ins Timeout —, während jeder Wert einzeln abgefragt antwortet. Deshalb wird die CyberPower-MIB immer Wert für Wert gelesen: ein paar hundert Millisekunden je Abfrage im lokalen Netz, und eine Karte, die nicht mehr antwortet, kostet weiterhin nur ein einziges Timeout.

Eine MIB fest wählen nur, um sie zu erzwingen, etwa um ein Gerät zum Vergleich auf den Standard festzunageln — oder wenn „USV testen" meldet, dass die reguläre Abfrage keine Antwort bekam, die Werte einzeln aber antworten. Dann CyberPower wählen: Automatisch beginnt immer mit einer Anfrage nach mehreren Werten, die eine solche Karte nie beantwortet.

NUT-Server (USB- und serielle USVs)

Eine USV ohne Netzwerkkarte wird über Network UPS Tools erreicht: Auf der Maschine, an der die USV steckt, läuft upsd, und PVE-UPS liest von dort über TCP 3493. Häufig existiert so ein Server bereits — Synology- und QNAP-NAS haben eine „USV-Server"-Option, ebenso TrueNAS und OPNsense; sonst genügt ein Raspberry Pi oder ein Proxmox-Host mit dem Paket nut-server.

Nötig sind drei Angaben: der Host, auf dem upsd läuft, der USV-Name wie in dessen ups.conf konfiguriert (upsc -l <host> listet die verfügbaren Namen) und optional Benutzer und Passwort — ein Standard-upsd erlaubt das Lesen von Variablen auch ohne beides.

NAS als NUT-Server (QNAP, Synology)

Beide Hersteller liefern ihre eigene, fest vorgegebene Einrichtung — die Werte sind nicht frei wählbar:

NASUSV-NameBenutzerKennwort
QNAPqnapupsadmin123456
Synologyupsupskeines

Bei beiden muss der Netzwerk-USV-Server aktiviert und die IP-Adresse der Appliance in der Liste der erlaubten Geräte eingetragen sein — sonst antwortet das NAS schlicht nicht, mit Abstand die häufigste Ursache für einen fehlschlagenden Test. Die Einstellung sitzt bei der USV-Konfiguration (QNAP: Systemsteuerung, externes Gerät; Synology: Systemsteuerung, Hardware & Energie); die genaue Bezeichnung unterscheidet sich je nach QTS- bzw. DSM-Version.

PVE-UPS ist ein strikt nur lesender NUT-Client: Es fragt ausschließlich die Variablenliste ab, sendet nie einen Befehl und betreibt kein upsmon. NUT dient als Gerätetreiber; Schwellwerte, Host-Logik und die Shutdown-Entscheidung bleiben in dieser Appliance. Auf den geschützten Hosts ist nichts einzurichten.
Das NUT-Protokoll ist unverschlüsselt und gehört in ein vertrauenswürdiges Netz. Läuft upsd auf einer Maschine, die PVE-UPS selbst herunterfährt, sollte genau dieser Host als „Dieser Host" markiert sein oder die höchste Shutdown-Reihenfolge haben — sonst verschwindet die Datenquelle mitten im Ausfall. Der Akkubetrieb-Countdown läuft in dem Fall zwar weiter (siehe Abschnitt 7), eine weiterhin erreichbare Quelle ist aber besser.

Testergebnis lesen

Unter der Ergebniszeile bietet „USV testen" die Details je Objekt — jedes Objekt einzeln abgefragt, mit seinem Wert oder dem Grund, warum es fehlt. Der Block klappt von selbst auf, sobald etwas nicht stimmt, und trennt damit die Fälle, die sonst gleich aussehen:

  • Nichts antwortet (jede Zeile ein Fehler): Adresse, Port oder Zugangsdaten stimmen nicht, oder eine Firewall blockiert UDP 161 (SNMP) bzw. TCP 3493 (NUT). Bei NUT zusätzlich prüfen, ob die LISTEN-Direktive von upsd diesen Host überhaupt umfasst — standardmäßig lauscht er nur auf localhost.
  • Manche Objekte antworten, andere melden noSuchObject / noSuchInstance (SNMP) bzw. „von diesem Treiber nicht geliefert" (NUT): Das Gerät veröffentlicht diese Werte schlicht nicht. Sobald das einen Auslöser betrifft, sagt der Test das im Klartext über der Tabelle — ein Treiber ohne battery.runtime macht etwa die Schwelle „Restlaufzeit unter (min)" dauerhaft wirkungslos. Stattdessen den Zeitgeber „Akkubetrieb länger als (s)" nutzen: Er läuft auf der eigenen Uhr der Appliance und funktioniert immer.
  • noSuchName unter SNMPv1: Das Objekt fehlt und v1 bricht eine Sammelabfrage ab, sobald ein Objekt fehlt — die reguläre Abfrage scheitert dann komplett, obwohl die übrigen Werte lesbar wären. Die USV nach Möglichkeit auf v2c umstellen.
  • Die reguläre Abfrage bekommt keine Antwort, jedes Objekt antwortet aber einzeln (SNMP): Die Karte verarbeitet keine Anfrage nach mehreren Werten auf einmal — manche CyberPower-Firmware lässt sie schlicht ins Timeout laufen. Die Zusammenfassung sagt das; die MIB auf CyberPower stellen, die Wert für Wert gelesen wird.
  • Alle RFC-1628-Objekte fehlen, alle Hersteller-Objekte antworten: normal bei einer APC-Karte ohne RFC-1628-Unterstützung. Im Modus Automatisch werden beide MIBs aufgelistet, die tatsächlich genutzte steht oben, und die Zeile über der Tabelle nennt sie. Es ist nichts zu ändern — die gezählten Objekte und die Hinweise zu Auslösern beziehen sich immer auf die genutzte MIB, nicht auf die unterlegene.
  • „veraltete Daten" (NUT): upsd antwortet, aber sein Treiber hat den Kontakt zur USV verloren. Die noch gelieferten Werte sind alt, deshalb gilt die USV als nicht erreichbar — Alarm, nie ein Shutdown. Den NUT-Treiber auf der Maschine neu starten.
  • Das Objekt für die Stromquelle fehlt oder meldet „unknown": Das Gerät antwortet, andere Werte kommen an, aber genau das Objekt, das sagt, ob es am Netz oder auf Akku läuft (upsOutputSource, bei APC upsBasicOutputStatus), liefert nichts Brauchbares. Daraus lässt sich nichts folgern, deshalb gilt die USV als nicht erreichbar — Alarm, nie ein Shutdown, und ein laufender Akku-Countdown läuft weiter. Die MIB-Einstellung prüfen; implementiert das Gerät das Objekt wirklich nicht, taugt es nicht als Shutdown-Quelle.
  • ups.status nennt weder OL noch OB (NUT): derselbe Fall auf der NUT-Seite. Die Variable ist da, trägt aber nur etwas wie CHRG, ALARM oder RB — oder ist leer —, und nichts davon sagt, woher der Strom kommt. Behandlung genau wie oben: nicht erreichbar, Alarm, nie ein Shutdown, ein laufender Countdown läuft weiter. Meistens eine Treiber-Eigenheit; den Treiber auf dem NUT-Server prüfen.
All diese Geräte haben geantwortet. PVE-UPS hält das bewusst von einem Gerät auseinander, das verstummt ist, denn „Shutdown bei reinem Kommunikationsverlust" (siehe Auslöser) greift nur bei Stille. Eine USV, die unbrauchbar antwortet, löst ihn nie aus — und ein Eintrag, der von vornherein gar nicht abfragbar ist, etwa eine ohne Adresse gespeicherte USV-Karte, ebenso wenig. Der Alarm sagt, welcher der beiden Fälle vorliegt, und schickt einen so nicht in ein Netz, das funktioniert.

6 Funktion & Logik

Die Engine fragt alle USVs parallel ab und wertet jede USV unabhängig aus. Jede Abfrage hat eine eigene Frist, abgeleitet aus den Timeout- und Wiederholungseinstellungen des jeweiligen Geräts — ein Server, der die Verbindung annimmt und dann verstummt, kann den Countdown der anderen also nicht aufhalten. Pro USV gibt es eine einfache Zustandsabfolge:

ONLINE Netzbetrieb  →  ON_BATTERY Stromausfall, USV im Akku  →  ausgelöst sobald eine Schwelle greift

Welcher Host fährt herunter?

Das entscheidet die Zuordnung jedes Hosts zu seinen USVs und seine Logik:

  • UND (ups_policy = all, Standard): Der Host fährt erst herunter, wenn alle ihm zugeordneten USVs ausgelöst haben — exakt das Verhalten für Server mit redundanten Netzteilen (je Netzteil eine USV). Solange eine USV noch Strom liefert, bleibt der Host an.
  • ODER (ups_policy = any): Der Host fährt herunter, sobald eine zugeordnete USV auslöst — für aufgeteilte, nicht redundante Last.

Mehrere fällige Hosts werden in Stufen abgeschaltet, gemäß dem Feld „Reihenfolge" — aufsteigend, die 0 kommt also zuerst: alles mit derselben Zahl wird gleichzeitig angewiesen, und die nächste Stufe startet erst, wenn diese durch ist. Der Host, der die Appliance selbst trägt (this_host), bildet unabhängig von seiner Zahl immer die letzte Stufe, damit er die übrigen noch abschalten kann. Tipp: den Appliance-Host an alle USVs hängen, damit er zuverlässig zuletzt fällig wird. Der Wizard zeigt die daraus entstehende Abschaltfolge live unter der Host-Liste an.

Jeder Befehl hat zusätzlich eine harte Obergrenze („Host-Shutdown-Timeout"). Beides zusammen bedeutet: eine Maschine, die nicht mehr antwortet, kann weder ihre Stufenpartner noch die nachfolgenden Stufen noch den Akku-Countdown selbst aufhalten. Das Reihenfolge-Feld also nur nutzen, wenn ein Ziel wirklich vor einem anderen herunter muss — sonst ist „gleiche Zahl" schneller und sicherer.

Erholt sich eine erforderliche USV (Netz kehrt zurück), wird ein noch nicht ausgeführter Shutdown wieder abgebrochen und der Zustand zurückgesetzt.

Ein bereits gesendeter Shutdown bleibt dagegen gesperrt — eine Maschine, die gerade herunterfährt, darf nicht ein zweites Mal den Befehl bekommen. Diese Sperre löst sich wieder, sobald jede USV so lange erreichbar und am Netz war, wie unter „Wieder scharf nach Netzrückkehr (min)" eingestellt ist (Vorgabe 5, leer = nie). Erst dann ist die Appliance für den nächsten Ausfall bereit: Solange die Sperre steht, fände ein zweiter Ausfall jeden Host als „bereits ausgelöst" vor, und auch der geplante Selbsttest sowie „Cluster wiederherstellen" bleiben ausgesetzt. Die Wartezeit gibt es, weil zurückgekehrtes Netz nicht dasselbe ist wie bleibendes Netz — ein Netz, das binnen einer Minute zweimal einbricht, darf dazwischen nicht wieder scharf werden. Eine nicht erreichbare USV gilt nie als „Netz ist zurück". Das Wiederherstellen eines vorbereiteten Clusters bleibt so oder so manuell; die Re-Armierung macht diesen Knopf nur wieder verfügbar, und das Ereignis sagt es dazu, wenn ein Cluster noch vorbereitet ist. Der Knopf „Zustand zurücksetzen" tut jederzeit dasselbe sofort.

Proxmox-VE-Cluster Beta

Die Cluster-Vorbereitung setzt Proxmox VE 9.2 oder neuer voraus. Alles in diesem und im nächsten Abschnitt hängt an disarm-ha, das mit 9.2 kam. Auf älteren Versionen wird HA nicht disarmt, und wo HA Gäste verwaltet, werden diese auch nicht clusterweit gestoppt; die Ceph-Wartungsflags werden trotzdem gesetzt. PVE-UPS erkennt das an der API selbst, nie an einer Versionsnummer, sodass auch ein Backport funktioniert.
Neu in 4.0.0 und bewusst als Beta gekennzeichnet. Der Mechanismus selbst ist zurückhaltend gebaut: Jeder Schritt wird überprüft statt angenommen, der Ablauf steht unter harten Zeitlimits, und die Voreinstellungen sind die sicheren. Wenig Erfahrung gibt es bislang mit der Vielfalt echter Cluster. Ohne Ihren Haken passiert hier nichts. Wenn Sie es einsetzen: Rückmeldungen sind willkommen über GitHub-Issues.

Dieser Abschnitt behandelt einen einfachen Proxmox-VE-Cluster. Läuft auf dem Cluster zusätzlich Ceph auf den eigenen Knoten, lesen Sie danach Hyperkonvergente Cluster (Ceph) — dieser Teil ist ein erheblich größerer Eingriff, mit eigenen Rechten.

Auf der Host-Karte im Kasten Proxmox-VE-Cluster „Cluster-Mitglied" ankreuzen — bei jedem Knoten des Clusters. Die Zuordnung erfolgt automatisch über den per API gelesenen Cluster-Namen — ein zweites Token oder ein eigener Konfigurationsabschnitt ist nicht nötig, und die Vorbereitung läuft genau einmal je Cluster, bevor dessen erster Knoten heruntergefahren wird. Der Haken entscheidet darüber, wer als Mitglied zählt: Ein Knoten ohne ihn wird umgangen statt einbezogen, er wird von „Ganzen Cluster als Einheit herunterfahren" nie mitgenommen, und seine eigenen Schalter haben kein Mitspracherecht. Was der Haken nicht abwählt, ist die Vorbereitung selbst — die wirkt naturgemäß auf den ganzen Cluster: HA wird clusterweit entwaffnet und mit dem Gäste-Stopp oder Ceph wird jeder Gast im Cluster gestoppt, auch die auf diesem Knoten. Bleibt der Haken auf einem Knoten aus, steht diese Maschine also ohne HA und ohne ihre Gäste da. Der geplante Selbsttest benennt einen solchen Knoten, damit der Widerspruch vor einem Stromausfall auffällt und nicht währenddessen.

Alle Schalter in diesem Kasten wirken auf den gesamten Cluster — Ceph-Wartungsflags, Armierungszustand des HA-Managers, der Gäste-Stopp und ob der Cluster als Einheit heruntergefahren wird — obwohl sie je Host-Karte eingestellt werden. Setzen Sie jeden davon deshalb bei allen Knoten eines Clusters gleich. Wo sie sich widersprechen, geht PVE-UPS von „mindestens ein Knoten hat es verlangt" aus (einen verlangten Schritt auszulassen kann den Storage kosten, einen ungefragten auszuführen kostet ein Wartungsflag) und schreibt eine Warnung, die beide Seiten benennt — so fällt der Widerspruch beim nächsten Selbsttest auf und nicht erst im Ausfall.

Auf einem einfachen Cluster erledigt sie das eine, was ein Shutdown je Knoten nicht leisten kann:

  • HA-Disarm — ohne ihn verschiebt der HA-Manager Dienste auf Knoten, die selbst gerade abgeschaltet werden. PVE-UPS disarmt mit resource-mode=ignore; die Gäste verlassen damit die HA-Verwaltung und pve-guests fährt sie in ihrer konfigurierten Reihenfolge herunter. Das ist nicht einstellbar, und zwar bewusst: Unter freeze bleiben die Gäste HA-verwaltet, pve-guests überspringt sie und der disarmte LRM stoppt sie nicht mehr — sie würden vom Poweroff hart beendet.

Der Schritt wird überprüft, nicht angenommen: Der Disarm wird abgefragt, bis der HA-Status tatsächlich disarmed meldet. Er steht unter einem harten Zeitlimit, denn er läuft, während der Akku leerläuft.

Dieses Zeitlimit („Zeitlimit HA-Disarm / Ceph-Flags", unter Auslöser) ist die Zeit, die der Disarm tatsächlich bekommt — nicht bloß eine äußere Notbremse: Das Budget wird von Schritt zu Schritt weitergereicht, ein höherer Wert kauft also wirklich mehr Geduld. Die Voreinstellung ist 60 s. Der langsame Teil ist der Disarm, denn der HA-Stack arbeitet in Runden von zehn Sekunden und jeder Knoten muss seinen Watchdog freigeben, bevor der Zustand von disarming auf disarmed wechselt. Unter etwa einer halben Minute lässt er sich meist gar nicht bestätigen. Jede Sekunde hier fehlt dem Shutdown, also erhöhen Sie den Wert bewusst — die Knoten dieses Clusters warten darauf. Läuft das Budget ab, nennt das Ereignis den Zustand, bei dem es aufgehört hat („noch beim Disarmen" heißt: mehr Zeit geben; ein Stack, der sich nie bewegt hat, ist ein anderes Problem) und was bereits erledigt war. Ein bereits disarmter Cluster — ein zweiter Ausfall, bevor Sie wiederhergestellt haben — wird in Ruhe gelassen statt erneut disarmt. Im Dry-Run wird nur protokolliert; es wird nichts geändert.

Die Vorbereitung sagt, wann sie beginnt, nicht nur, wie sie ausging: Ein Ereignis nennt, was sie vorhat, wie viele Knoten des Clusters ausgelöst haben und wie lange die Knoten darauf warten dürfen. Zwischen dieser Zeile und dem Ergebnis wartet der Shutdown der Cluster-Knoten mit Absicht.

Schlägt die Vorbereitung fehl, läuft der Shutdown standardmäßig weiter. Das ist die sicherere Einstellung: Ein fehlgeschlagener Disarm lässt den HA-Manager armiert, und ein armierter HA-Manager stoppt die Gäste selbst — unruhiger, aber die Maschinen fahren herunter. Die Gegenoption („Shutdown abbrechen, wenn die Cluster-Vorbereitung fehlschlägt", unter Auslöser) bedeutet, dass eine fehlgeschlagene Vorbereitung den ganzen Cluster laufen lässt, bis der Akku leer ist.

Alle Gäste zuerst stoppen, ohne Ceph (optional)

Ohne weiteres Zutun stoppen bei einem einfachen Cluster die Knoten ihre Gäste selbst, während sie ausschalten — in umgekehrter startup-Reihenfolge, Gruppe für Gruppe, mit den Wartezeiten jeder Gruppe. Bei vielen Order-Gruppen kann das länger dauern, als der Akku hält. „Alle Gäste clusterweit zuerst stoppen" (standardmäßig aus) ersetzt das durch den Schritt aus der Ceph-Prozedur: Bevor der erste Knoten herunterfährt, wird jede VM und jeder Container des Clusters außer dieser Appliance zum Herunterfahren aufgefordert — alle gleichzeitig, parallel —, und das Ergebnis wird durch erneutes Lesen der Gästeliste überprüft.

  • Die Startreihenfolge wird ignoriert, und zwar bewusst: Es geht darum, fertig zu sein, bevor der Akku es ist. Eine Abhängigkeit zwischen einer Anwendung und ihrer Datenbank wird nicht berücksichtigt.
  • Der Schritt hat sein eigenes Budget, „Zeitlimit Gast-Shutdown", und Gäste, die nach „Gäste hart stoppen nach" noch laufen, werden hart gestoppt — siehe den Gäste-Shutdown weiter unten; die Details gelten unverändert.
  • Wo HA Gäste verwaltet, muss HA vorher disarmt werden (Proxmox VE 9.2+ und der HA-Schalter), sonst startet der HA-Manager sie so schnell wieder, wie sie stoppen. Geht das nicht, wird der Schritt mit einer Warnung übersprungen, und die Knoten stoppen ihre Gäste wie bisher selbst.
  • Der eigene Gast dieser Appliance muss ausgewählt sein — siehe der eigene Gast der Appliance. Bis dahin wird gar kein Gast gestoppt.
  • Benötigt VM.Audit und VM.PowerMgmt (Tabelle unten).

Mit der Ceph-Option gehört der Gäste-Stopp immer zum Ablauf — die Host-Karte zeigt ihn dann angehakt und gesperrt, und wird Ceph wieder abgewählt, steht der Kasten wieder so wie vorher.

Der Cluster fährt als Einheit herunter

Die Vorbereitung wirkt naturgemäß clusterweit — sie disarmt HA für den gesamten Cluster und stoppt mit dem Gäste-Stopp (oder der Ceph-Option) jeden Gast darin. Der Shutdown selbst ist dagegen hostweise: Ein Knoten ist fällig, wenn seine USVs das sagen. Beides muss nicht übereinstimmen, und wenn es das nicht tut, bleibt ein halbierter Cluster zurück.

Dafür gibt es „Gesamten Cluster als Einheit herunterfahren" (standardmäßig an): Sobald ein Knoten des Clusters fällig ist, wird jeder Knoten davon heruntergefahren — auch die, deren eigene USV nicht ausgelöst hat. Sie gehen in der üblichen order-Reihenfolge, der Host der Appliance zuletzt, und das Eventlog nennt zu jedem, warum er mitgenommen wurde.

Schalten Sie es nur bei einem einfachen Cluster aus, bei dem HA die Gäste eines einzelnen ausfallenden Knotens lieber auf die übrigen verschieben soll; dort ist ein Teil-Shutdown ein gutes Ergebnis. Mit dem Gäste-Stopp sollte es an bleiben, sonst haben die weiterlaufenden Knoten ihre Gäste umsonst verloren; bei Ceph muss es an bleiben — was ein halb heruntergefahrener hyperkonvergenter Cluster bedeutet, steht im nächsten Abschnitt.

Eine USV, die verstummt, löst nichts aus. Stirbt das Management-Netz einer USV mit dem Ausfall — ein sehr häufiger Aufbau, bei dem der Switch an der ausfallenden USV selbst hängt —, sieht PVE-UPS ein unerreichbares Gerät, keinen Stromausfall, und der Fail-safe verweigert dafür bewusst jeden Shutdown („NO shutdown will be triggered"). Knoten, die nur von dieser USV gespeist werden, bleiben also stehen. Zwei Abhilfen, die sich kombinieren lassen: „Gesamten Cluster als Einheit herunterfahren" an lassen, damit diese Knoten trotzdem mit den übrigen heruntergefahren werden, und unter Auslöser „Shutdown bei reinem Kommunikationsverlust nach (min)" setzen, wenn eine verstummte USV für sich genommen als Ausfall gelten soll. Der Selbsttest warnt, wenn die Knoten eines Clusters an USVs hängen, die unabhängig voneinander auslösen können.

Jeder Knoten braucht einen eigenen Host-Eintrag mit eigener API-URL. Der Shutdown erreicht den Knoten hinter der jeweiligen API-URL (siehe Abschnitt 4.1) — ein Knoten ohne Eintrag ist also ein Knoten, den niemand herunterfährt, ganz gleich, was die Namen sagen, und außerdem einer, den die „als Einheit"-Regel nicht mitnehmen kann. Der Selbsttest vergleicht deshalb die Knotennamen des Clusters mit den Host-Einträgen und warnt vor jedem Knoten, den niemand herunterfahren würde, unter Nennung beider Listen. Unterscheidet sich nur Groß-/Kleinschreibung oder ein Domain-Anhang, nennt die Warnung den vermutlich gemeinten Knoten; ein bloß deaktivierter Eintrag wird als deaktiviert gemeldet und nicht als falsch benannt.

pveum role add UpsCluster -privs "Sys.Audit Sys.Console"

pveum role add UpsCluster -privs "Sys.Audit Sys.Console VM.Audit VM.PowerMgmt"

Anschließend die Rolle zuweisen — beide Zeilen, siehe den Hinweis zur Privilege Separation weiter unten:

pveum acl modify / -user ups@pve -role UpsCluster
pveum acl modify / -token 'ups@pve!shutdown' -role UpsCluster

Der Selbsttest hält sich an dieselbe Regel: Er verlangt ein Recht nur dort, wo die Funktion eingeschaltet ist und dieser Cluster sie überhaupt ausführen kann. Bei einer Version ohne disarm-ha wird nie Sys.Console eingefordert — eine Warnung über ein fehlendes Recht bedeutet also immer etwas, das Sie wirklich brauchen.

Die Schaltfläche „Testen" auf der Host-Karte prüft diese Rechte mit, sobald die Cluster-Option angehakt ist: Sie benennt jedes fehlende Recht, meldet den gefundenen Cluster (Name, Knotenanzahl, Ceph und HA-Armierungszustand) und weist darauf hin, wenn der Knoten gar kein Cluster-Mitglied ist. Ein fehlendes Cluster-Recht wird als Warnung gemeldet, nicht als Fehler — die Verbindung selbst funktioniert ja. Zu jedem Namen steht dabei, wofür er gebraucht wird („Sys.Console (HA disarm)"), sodass die Entscheidung über die Vergabe ohne diese Seite fällt. Darunter listet ein Detail-Ausklapper jede Abfrage mit ihrem Ergebnis auf (er öffnet sich von selbst, wenn etwas nicht stimmt), sodass sichtbar wird, was die einzelnen Endpunkte tatsächlich geantwortet haben — statt nur der Zusammenfassungszeile. Eine Abfrage, die nur eine nicht angehakte Option braucht — etwa die Gästeliste ohne Gäste-Stopp —, erscheint als „nicht lesbar (nicht benötigt)" und lässt den Ausklapper geschlossen.

Sys.Console gewährt faktisch Shell-Zugriff auf die Knoten. Deshalb ist der HA-Disarm ein eigener Schalter: Wer ihn nicht vergeben möchte, lässt den Schalter aus und nimmt die Sys.Audit-Zeile oben. Zu beachten ist außerdem, dass API-Tokens standardmäßig Privilege Separation aktiv haben und einen eigenen ACL-Eintrag benötigen — die Rechte des Benutzers genügen nicht, weshalb die beiden acl modify-Befehle oben beide erforderlich sind.
Ein disarmter HA-Stack wird auch dann gemeldet, wenn kein Gast HA-verwaltet ist. Beides ist unabhängig voneinander: Das Disarmen setzt das Fencing clusterweit aus, und dabei bleibt es, bis jemand wieder armiert — deshalb richten sich Selbsttest und „Cluster wiederherstellen" nach dem Armierungszustand, nicht danach, ob HA gerade etwas verwaltet.
Auf Proxmox VE älter als 9.2 gibt es kein disarm-ha. Setzen Sie stattdessen die Datacenter-Option shutdown_policy=freeze; die Voreinstellung conditional verschiebt HA-Dienste auf Knoten, die gerade herunterfahren, und migrate ist noch ungünstiger, weil der LRM den Shutdown dann verzögert, bis alles wegmigriert ist. Der Selbsttest warnt vor beidem.

Danach bleibt der Cluster vorbereitet. Ein automatisches Wiederarmieren gibt es nicht: HA zurückzuholen, während Knoten noch hochfahren, ist eine Ermessensentscheidung. Der Selbsttest weist weiterhin darauf hin, dass HA disarmt ist (und die Flags gesetzt sind, wo sie es waren), und im Dashboard erscheint die Schaltfläche „Cluster wiederherstellen" — sie armiert HA wieder und löscht die Flags, jeweils überprüft, und erscheint nur, solange es tatsächlich etwas rückgängig zu machen gibt. Da die Appliance zuletzt heruntergefahren wird und mit dem Rest zurückkommt, prüft sie die Cluster einmal beim Start — die Rückstände stehen dadurch sofort im Dashboard statt erst beim nächsten planmäßigen Selbsttest. Während eines laufenden Shutdowns ist die Schaltfläche ausgeblendet, und die API lehnt die Anfrage ab: HA dort wieder zu armieren würde die Vorbereitung genau in dem Moment rückgängig machen, in dem sie ihre Aufgabe erfüllt.

Bei einem einfachen Cluster fasst PVE-UPS einzelne Gäste nie an: Beim Poweroff werden sie ohnehin in ihrer konfigurierten Reihenfolge gestoppt — vom LRM, solange HA armiert ist, und von pve-guests, sobald er disarmt ist — und das Problem, das der HA-Disarm löst, ist ausschließlich das Verschieben auf andere Knoten danach. Nur der Gäste-Stopp ändert das — für sich angehakt oder als Teil der Ceph-Option.

Hyperkonvergente Cluster (Ceph) Beta

Das ist ein erheblich größerer Eingriff als der Abschnitt oben. Mit angehaktem „Ceph-Cluster vorbereiten" stoppt PVE-UPS jede VM und jeden Container des Clusters, bevor der erste Knoten heruntergefahren wird — es wird nicht bloß HA umgestellt. Außerdem braucht es drei weitere Rechte, der eigene Gast dieser Appliance muss ausgewählt sein, damit er verschont wird, und dieser Gast darf nicht auf Ceph-Storage liegen. Lesen Sie diesen Abschnitt, bevor Sie es einschalten.

Alles aus dem vorigen Abschnitt gilt zusätzlich; hier kommen zwei Schritte dazu. Die Reihenfolge unten ist die Reihenfolge der Ausführung, und sie ist entscheidend — genau deshalb stehen die Schalter auf der Host-Karte in derselben Reihenfolge:

  1. HA-Disarm — muss zuerst kommen, sonst startet der HA-Manager jeden Gast wieder, den Schritt 2 gerade gestoppt hat.
  2. Alle Gäste werden clusterweit gestoppt — jede VM und jeder Container außer dieser Appliance selbst.
  3. Ceph-Wartungsflags — noout, nobackfill, norecover und norebalance werden gesetzt, damit Ceph nicht mit der Wiederherstellung beginnt, während die OSDs nacheinander wegfallen. Entspricht ceph osd set noout und den übrigen Befehlen.

Die Schritte 2 und 3 sind eine Option, und sie ist standardmäßig aus: Viele Cluster laufen auf ZFS-Replikation oder gemeinsamem NFS/iSCSI, und dies ist der einzige Teil, der in eine Storage-Ebene schreibt. Auf einem Cluster ohne Ceph wird sie übersprungen, statt versucht und als Fehler gemeldet zu werden, und die zugehörigen Rechte werden nicht gebraucht. Schritt 2 gibt es auch für sich, für Cluster ohne Ceph (siehe oben), mit Ceph lässt er sich aber nicht abschalten: Dort ist er keine Option, sondern der erste Schritt der offiziellen Prozedur, und ein Haken, dessen Fehlen den Cluster beim Stromausfall hängen lässt, wäre eine Falle. Die Host-Karte zeigt ihn angehakt und gesperrt, solange Ceph an ist.

Die Flags werden überprüft, nicht angenommen: Die Sammel-Aktualisierung läuft asynchron (sie liefert nur eine Worker-Kennung), deshalb werden sie zurückgelesen — notfalls einzeln gesetzt.

Lassen Sie „Gesamten Cluster als Einheit herunterfahren" hier an. Ein teilweise heruntergefahrener hyperkonvergenter Cluster hat keinen sinnvollen Zustand. Ein echtes Beispiel aus einem Vier-Knoten-Cluster: Nur eine USV löste aus, also gingen zwei Knoten herunter, während die beiden anderen weiterliefen. Die Vorbereitung hatte da bereits jeden Gast gestoppt und HA clusterweit disarmt, und zwei der drei Ceph-Monitore lagen auf den wegfallenden Knoten — die Überlebenden standen also ohne Gäste, ohne HA und ohne Storage-Quorum da. Ob Sie einen hyperkonvergenten Cluster ganz oder gar nicht herunterfahren, ist eine echte Wahl; ihn halb herunterzufahren ist keine.

Warum die Gäste zuerst stoppen müssen

Das ist der Teil, den ein Shutdown je Knoten falsch macht. Sich selbst überlassen, stoppt jeder Knoten beim Ausschalten seine eigenen Gäste — das klingt sauber und hängt dann. Bei den üblichen size=3/min_size=2 ist der Pool nach dem ersten Knoten noch in Ordnung, doch sobald die OSDs des zweiten Knotens weg sind, fällt er unter min_size. Die auf dem verbliebenen Knoten noch laufenden Gäste blockieren nun auf IO: Ihr Shutdown wird nie fertig, dieser Knoten geht also nie aus, und der Akku ist leer, während der Cluster halb unten ist.

Proxmox dokumentiert dieselbe Reihenfolge („Shutdown Proxmox VE + Ceph HCI cluster"): erst alle Ceph-Clients stoppen, dann die OSD-Flags setzen, dann die Knoten ausschalten. PVE-UPS folgt ihr. Alle laufenden Gäste werden gleichzeitig zum Herunterfahren aufgefordert — höchstens acht Anfragen zeitgleich, denn vierzig Gäste nacheinander zu fragen kostet je einen Verbindungs-Timeout — und das Ergebnis wird überprüft, indem die Gastliste des Clusters neu gelesen wird; aus der Antwort der API wird es nie geschlossen.

Zwei Zeitlimits unter Auslöser steuern das, und sie sind bewusst getrennt:

  • „Zeitlimit Gast-Shutdown" (Vorgabe 300 s) — das Budget für das Stoppen der Gäste. Es wächst mit ihrer Zahl und ihrer Abschaltdauer; das Budget für HA/Ceph daneben bemisst sich an HA-Runden von zehn Sekunden und schwankt kaum. Eine Zahl könnte beides nicht leisten, und zusammengelegt würden die Gäste die Zeit des Disarms aufbrauchen.
  • „Gäste hart stoppen nach" (Vorgabe 120 s) — wann ein Gast, der die Anforderung ignoriert, hart gestoppt wird. Der Wert wird auch als Zeitlimit an den Proxmox-Aufruf selbst übergeben, damit der Abbruch auch dann erfolgt, wenn diese Appliance direkt danach das Netz verliert. Leer lassen heißt: nie erzwingen — ein hängender Gast lässt die Vorbereitung dann fehlschlagen und wird im Eventlog namentlich genannt.

Behalten Sie die Summe im Blick. Zwischen dem Auslösen und der Aufforderung an den letzten Knoten liegen im ungünstigsten Fall das HA/Ceph-Budget plus das Gast-Budget plus das Zeitlimit je Knoten — mit den Vorgaben 420 s. Die Einstellungsseite zeigt diese Zahl an, und der Selbsttest warnt, wenn der Auslöser „geschätzte Restlaufzeit unter" später greift, als der Ablauf braucht. Er warnt nur; er verstellt nie selbst einen Auslöser.

Knoten-Reihenfolge: Proxmox empfiehlt, zuerst die Knoten ohne Ceph-Monitor auszuschalten. PVE-UPS liest die Monmap und weist im Host-Test und im Selbsttest darauf hin, wenn Ihre „Reihenfolge"-Werte dem widersprechen — sortiert sie aber nie selbst um. Ihre Reihenfolge ist ausdrückliche Konfiguration, und sie zur Ausfallzeit still zu überstimmen würde die auf dem Dashboard angezeigte Abfolge zur Lüge machen.

Nicht berücksichtigt: Die Gäste werden parallel gestoppt, nicht in ihrer startup-Reihenfolge — eine Abhängigkeit zwischen einer Anwendung und ihrer Datenbank wird also nicht beachtet. Ziel ist hier, die IO schnell zum Stillstand zu bringen, und der Grund dafür ist der Akku.

Der eigene Gast dieser Appliance

„Alle Gäste stoppen" darf die Appliance nicht einschließen, die das Stoppen veranlasst. Unter Auslöser → Diese Appliance wählen Sie die VM oder den Container, in dem PVE-UPS läuft, aus der Liste aus. Bewusst eine Liste und kein Eingabefeld: Eine vertippte ID bedeutet, dass sich diese Appliance mitten im Stromausfall selbst abschaltet. Läuft sie tatsächlich woanders — Docker auf einem NAS, Blech, ein anderer Cluster —, wählen Sie „kein Gast dieses Clusters".

Die Auswahl bewirkt zweierlei. Sie markiert den einen Gast, der nie gestoppt wird, und sie setzt „Dieser Host" auf der Host-Karte des Knotens, auf dem dieser Gast läuft, damit dieser Knoten zuletzt heruntergefahren wird. Der Haken erscheint dann als aus der Auswahl übernommen, statt doppelt gepflegt zu werden; ohne Auswahl bleibt er ein manueller Schalter wie bei einem Standalone-Host. Wird die Appliance später auf einen anderen Knoten migriert, meldet das der Selbsttest.

Solange nichts ausgewählt und „kein Gast dieses Clusters" nicht gesetzt ist, werden die Gäste gar nicht gestoppt. Das Eventlog sagt das deutlich, und der Shutdown läuft ohne diesen Schritt weiter — genau so, wie es frühere Versionen taten. Verweigern ist hier die einzig sichere Antwort: Die Alternative wäre Raten, und ein falscher Tipp schaltet die Maschine ab, die den Shutdown ausführt.

Dieser Container darf nicht auf Ceph-Storage liegen. Er ist der eine Gast, der den Cluster überleben muss, den er herunterfährt. Auf Ceph tut er das nicht: Sobald die OSDs der abschaltenden Knoten den Pool unter min_size drücken, antwortet seine eigene Platte nicht mehr, und er kann nichts mehr herunterfahren — mitten im Stromausfall. Verwenden Sie local-lvm, local-zfs oder einen Verzeichnis-Storage. install.sh setzt das durch: Ceph-gestützte Storages werden bei der automatischen Auswahl übersprungen und bei ausdrücklicher Angabe über --storage abgelehnt, sofern Sie nicht --allow-ceph-storage mitgeben. Zur Laufzeit weisen Host-Test, Selbsttest und Dashboard darauf hin, falls die Appliance doch auf Ceph liegt.

Warum VM.Audit wichtiger ist, als es aussieht. /cluster/resources filtert nach Rechten, statt abzulehnen: Ein Token ohne VM.Audit bekommt eine völlig erfolgreiche Antwort mit leerer Gastliste. „Cluster wiederherstellen" startet die Gäste nicht wieder — sie kommen über ihre onboot-Einstellung zurück, wenn die Knoten hochfahren.

7 Fail-safe & Sonderfälle

Grundprinzip: Ein Kontaktverlust zur USV ist kein bestätigter Stromausfall — die USV antwortet vielleicht nur kurz nicht, oder ein Switch dazwischen ist weg. Standardmäßig löst ein Kommunikationsverlust daher nur Alarm aus, keinen Shutdown. Zwei optionale Einstellungen verfeinern das:

  • Shutdown bei Verlust fortsetzen (Standard an): Reißt der Kontakt ab, nachdem bereits ein Akkubetrieb bestätigt war, läuft ein gestarteter Akkubetrieb-Countdown auf der lokalen Uhr weiter und löst bei Ablauf aus. Nur dieser zeitbasierte Auslöser überlebt den „blinden" Zustand (Restlaufzeit und Ladestand sind dann nicht lesbar). Hatte ein Auslöser (z. B. Battery-Low oder Ladestand-Schwelle) dagegen schon vor dem Verbindungsabriss gegriffen, bleibt er bestehen und wird nicht auf den Zeitcountdown zurückgestuft. Countdown und ausgelöster Zustand überleben auch einen Neustart des Dienstes: beides wird auf Platte gemerkt und beim Start wiederhergestellt (max. 24 h alt).
  • Shutdown nach X Minuten reinem Verlust (Standard aus): Behandelt einen reinen Kommunikationsverlust (ohne vorher bestätigten Akkubetrieb) nach X Minuten doch als Ausfall. Bewusstes Opt-in für Umgebungen, in denen ein längerer Kontaktverlust als kritisch gilt. Er greift nur bei Stille: Ein Gerät, das antwortet, dessen Antwort aber unbrauchbar ist — keine verwertbare Stromquelle, keines der Objekte der gewählten MIB, ein ups.status, der weder OL noch OB nennt, oder ein NUT-Server, der mit ERR DATA-STALE, DRIVER-NOT-CONNECTED, ACCESS-DENIED oder UNKNOWN-UPS antwortet —, gilt für alles andere als nicht erreichbar, aber nie als Kommunikationsverlust. Die Verbindung steht ja sichtbar; der Alarm sagt, welcher der beiden Fälle vorliegt. Dasselbe gilt für einen Eintrag, der gar nicht abgefragt werden kann (eine USV-Karte ohne Adresse, etwa aus einem Backup-Import): Sie hat nie ein Paket geschickt, also auch keinen Hinweis auf den Strom geliefert, und bleibt, was sie überall sonst ist — ein Alarm und eine Verweigerung, die von ihr versorgten Hosts herunterzufahren, kein Befehl dazu.

8 Auslöser & Schwellen

Es genügt eine zutreffende Bedingung. Alle Werte sind im Wizard änderbar (Feld leeren = Bedingung aus); Schwellen lassen sich global setzen und pro USV überschreiben.

Wie „länger auf Akku als“ gemessen wird. PVE-UPS misst den Ausfall mit der eigenen Uhr, ab dem Poll, in dem die Umschaltung auf Akku erstmals gesehen wurde. Der Zähler, den die USV selbst meldet, wird bewusst nicht verwendet: Der Standard legt diesen Wert nur für den Akkubetrieb fest, und eine Karte, die den Wert des vorigen Ausfalls behält statt ihn zu löschen, ließe den allerersten Poll eines neuen Ausfalls so aussehen, als wäre die Schwelle längst überschritten. Der Gerätezähler wird gar nicht gelesen. Der laufende Timer übersteht einen Neustart des Dienstes, geht bei einem Update oder Reboot also nicht verloren; nur wenn dieser gespeicherte Timer unbrauchbar ist (fehlt oder älter als ein Tag), beginnt eine Appliance, die in einen bereits laufenden Ausfall startet, bei null zu zählen — und Restlaufzeit, Ladung und „Akku leer“ lesen frische Werte und sind davon nicht betroffen. Die Statusseite nennt, ob überhaupt eine Zeit gemessen werden konnte.

Ein wiederhergestellter Timer wartet auf die Bestätigung der USV. Diese Appliance fährt ihren eigenen Host zuletzt herunter, jeder Ausfall endet also mit ihrem Neustart — und sie findet einen gespeicherten Timer vor, der „seit drei Stunden auf Akku“ sagt. Genau dann konvergiert ein Switch noch und fährt eine SNMP-Karte noch hoch, und ein ungeprüft übernommener Timer würde die eben erst wieder gestarteten Maschinen sofort erneut herunterfahren. Deshalb löst nichts, was aus der Zustandsdatei kommt, einen Shutdown aus, bevor ein Poll des neu gestarteten Dienstes geantwortet hat. Diese Antwort klärt beides: Bei Netzbetrieb wird alles Wiederhergestellte verworfen, bei weiterhin Akkubetrieb wird der Auslöser aus der vollen wiederhergestellten Zeit im selben Poll bestimmt. Ein Neustart mitten im Ausfall kostet damit nichts, denn dort ist die USV per Definition erreichbar. Verloren geht der Countdown nur, wenn sich die USV nach dem Neustart nie wieder meldet — und dann hat die Appliance keinerlei Beleg dafür, dass der Ausfall überhaupt noch läuft, also handelt sie nicht. Solange ein Timer zurückgehalten wird, sagt das Dashboard das, statt auf einen Shutdown herunterzuzählen, der nicht kommt. Ein zurückgehaltener Timer gilt außerdem nicht als laufender Ausfall für die Prüfungen, die während eines Ausfalls pausieren: Selbsttest, Startprüfungen und „Cluster wiederherstellen“ bleiben verfügbar — und genau darauf kommt es an, denn eine nach dem Neustart der Appliance noch stumme USV ist der Moment, in dem der vom letzten Ausfall vorbereitete Cluster zurückgeholt werden muss.

Schlägt eine Shutdown-Anfrage fehl — ausgelastete API, abgebrochene Verbindung oder ein Knoten, der schlicht zu lange zum Antworten braucht —, wird dieser Host in den folgenden Polls erneut angefragt, insgesamt dreimal, und jeder Versuch steht im Eventlog. Eine wiederholte Anfrage an eine Maschine, die ohnehin herunterfährt, schadet nicht; nicht erneut zu fragen ließe sie bis zum leeren Akku weiterlaufen. Kehrt der Netzstrom zurück, während ein Host noch wiederholt wird, wird die Episode wie jede andere abgeschlossen: Die Appliance geht zurück auf ONLINE und schreibt ein kritisches Ereignis, das festhält, dass diese Maschine nie heruntergefahren wurde und noch läuft.

Werte außerhalb eines sinnvollen Bereichs werden korrigiert, nicht befolgt. Ein Poll-Intervall von null oder ein negativer Timeout fällt auf den Standard zurück und erzeugt ein Ereignis, das die Einstellung benennt. Das ist Absicht: Die Konfiguration stattdessen abzulehnen hieße, dass die Appliance nicht mehr startet — und damit gar nichts mehr schützt.

9 Monitoring / REST

Zwei lesende Endpunkte stehen ohne Authentifizierung und ohne Secrets zur Verfügung:

  • GET /api/status — kompletter Zustand: Appliance, alle USVs, Hosts, Shutdown-Status, die Benachrichtigungsziele samt Ergebnis ihrer letzten Zustellung (webhooks, bewusst ohne die URL) sowie die Ereignisse der letzten 48 h inkl. Severity-Zusammenfassung.
  • GET /api/health — 200, wenn die Engine läuft (mit Version und Erreichbarkeit der USVs), sonst 503. Ideal für Uptime-Checks. Zusätzlich werden die Shutdown-Ziele gemeldet: hosts_total, hosts_ok (letzter Selbsttest hat Token und Recht bestätigt), hosts_selftest_ok und hosts_selftest_at, die Benachrichtigungsziele (webhooks_total, webhooks_ok — ein Ziel gilt als ok, bis ein Versand nachweislich fehlgeschlagen ist, ein nie versuchtes liest sich also nicht als defekt) sowie dry_run. Diese Werte sind rein informativ — ein kaputtes Token macht aus dem Endpunkt keine 503, weil die Appliance selbst ja weiterarbeitet. Wer darauf alarmieren will, wertet hosts_selftest_ok, webhooks_ok und dry_run separat aus: Eine Appliance im Trockenlauf besteht hier jede Prüfung, antwortet ok und fährt nichts herunter.
curl http://<container-ip>:8080/api/status | jq
# nur kritische Ereignisse der letzten 48 h:
curl -s http://<container-ip>:8080/api/status \
  | jq '.events[] | select(.severity=="critical")'

Alle ändernden Endpunkte (Wizard speichern, Test-Shutdown) sind passwortgeschützt.

Ereignisprotokoll, Webhook-Nachrichten und API-Meldungen sind einheitlich englisch — unabhängig von der gewählten Oberflächensprache. Das hält Auswertung und Monitoring über Installationen hinweg konsistent.

Verlauf

Der Reiter Verlauf zwischen Dashboard und Einstellungen zeigt jede USV im Zeitverlauf: Restlaufzeit, Last und Ladung, mit dem Stromzustand als farbigem Hintergrund — Akkubetrieb, Shutdown ausgelöst, nicht erreichbar, Bypass. Ereignisse aus dem Ereignisprotokoll erscheinen als Markierungen: Warnungen und kritische Ereignisse immer, informative (etwa der Selbsttest) auf Wunsch. Mit der Maus über dem Diagramm stehen die Werte zu diesem Zeitpunkt und die Ereignisse an der Markierung daneben.

  • Zeiträume von 1 Stunde bis 90 Tage sowie „Alles" — oder ein beliebiger Beginn und ein beliebiges Ende in Von und Bis; diese beiden Felder zeigen immer den gerade angezeigten Zeitraum. Zum Hineinzoomen über das Diagramm ziehen, Doppelklick führt zum gewählten Zeitraum zurück; ein fester Zeitraum wird nicht unter Ihnen aktualisiert.
  • Eine USV: oben die Restlaufzeit in Minuten, darunter Last und Ladung in Prozent — zwei Felder auf einer Zeitachse statt eines Diagramms mit zwei Skalen. Die gestrichelte Linie ist der Auslöser „Restlaufzeit unter", den diese USV tatsächlich verwendet; so ist zu sehen, wie knapp ein Ausfall daran vorbeiging.
  • Alle (bei mehr als einer USV): eine Messgröße für jede USV in einem Diagramm, darunter je USV ein Statusstreifen.
  • Die Ausfall-Tabelle listet jeden Abschnitt im Akkubetrieb im Zeitraum — Beginn, Dauer, niedrigste Restlaufzeit und Ladung, höchste Last, ob ein Shutdown ausgelöst wurde. Ein Klick auf eine Zeile zoomt das Diagramm auf diesen Ausfall.
  • CSV lädt die Rohwerte des angezeigten Zeitraums herunter.

Aufgezeichnet wird ein Wert je USV und Minute im Netzbetrieb, einer je Abfrage im Akkubetrieb und einer bei jedem Zustandswechsel — etwa 1.440 Zeilen je USV und Tag, ein paar MB je USV über 90 Tage. Er liegt in history.db neben dem Ereignisprotokoll (unter Docker im selben Volume), ist nicht Teil der Konfigurationssicherung, und „Log leeren" lässt ihn stehen. Geschrieben wird im Hintergrund: Eine langsame oder volle Platte kostet den Verlauf, nie den Shutdown.

Unter Einstellungen → System lässt sich die Aufzeichnung abschalten, die Aufbewahrung in Tagen festlegen (1–365, Vorgabe 90) und der Verlauf löschen. Aus beendet die Aufzeichnung und blendet den Reiter aus; Aufgezeichnetes bleibt, bis es abläuft. Eine Neuinstallation zeichnet von Anfang an auf; nach einem Update von einer früheren Version bleibt es aus, bis Sie es einschalten — ein Update schreibt also nie ungefragt auf eine Platte, die niemand dafür bemessen hat.

Webhook-Benachrichtigungen

Optional wird jedes wichtige Ereignis per HTTP-POST an eine URL Ihrer Wahl geschickt (Einstellungen, Abschnitt 4). Es lassen sich beliebig viele Webhooks anlegen — eine Karte je Ziel, jeweils mit eigenem Format, eigenem Schweregrad-Filter und eigener Testschaltfläche. Der Versand läuft parallel und wird einzeln gemeldet; ein nicht erreichbares Ziel kostet den anderen also nicht ihre Benachrichtigung.

Ein Ziel, das nicht mehr funktioniert, sagt das. Ein abgelaufenes Token oder ein gelöschter Connector scheiterte bisher unsichtbar — man erfuhr davon bei dem Ausfall, über den man nicht informiert wurde. Der erste Fehlschlag nach einem erfolgreichen Versand steht jetzt im Eventlog, die Webhook-Karte zeigt den letzten Fehler an, bis ein Versand wieder gelingt, und die Appliance-Karte auf dem Dashboard bekommt eine Zeile „Benachrichtigungen“, solange irgendein Ziel gestört ist — auf die Einstellungsseite schaut während eines Ausfalls niemand. Benachrichtigungen bleiben durchgehend „best effort“: Sie werden nie wiederholt, und ein fehlschlagendes Ziel verzögert oder beeinflusst niemals einen Shutdown.

10 Updates & Betrieb

Updates lassen sich direkt im Webinterface hochladen; ein schmaler, privilegierter Begleitdienst wendet sie an (die App selbst bleibt unprivilegiert). Nach dem Upload wird das Update typischerweise innerhalb weniger Sekunden eingespielt. Über das Webinterface können zudem Konfiguration exportiert/importiert, NTP-Server und Zeitzone gesetzt und das Ereignisprotokoll eingesehen/geleert werden.

Das Webinterface aktualisiert sich nach einem Update zuverlässig selbst: Die Seite wird nie zwischengespeichert, und jedes geladene Skript bzw. Stylesheet trägt eine Kennung, die sich mit der Datei ändert — der Browser kann also nicht weiter die vorherige Fassung ausliefern. War ein Tab während des Neustarts geöffnet, erscheint oben ein Hinweis mit der Schaltfläche „Neu laden“; bis dahin läuft dort noch die alte Oberfläche.

Hinweis: Die Zeitzone (Abschnitt System, z.B. Europe/Berlin) sollte gesetzt werden, da der Container sonst in UTC läuft. Die Selbsttest-Startzeit gilt in dieser lokalen Zeit; nach dem Setzen der Zeitzone startet der Dienst kurz neu.

Selbsttest der Ziel-Verbindungen

Die Appliance prüft selbstständig je Host, ob API-Token und das jeweilige Power-Management-Recht noch funktionieren — Sys.PowerMgmt bei Proxmox VE, Sys.PowerManagement beim Backup Server —, damit abgelaufene oder zurückgezogene Zugangsdaten lange vor dem Ernstfall auffallen. Gesteuert wird das über zwei Einstellungen im Abschnitt System: eine Startzeit (volle Stunde) und ein Intervall von 15 Minuten bis 24 Stunden. Beide zusammen ergeben feste Tageszeiten: Startzeit 09:00 mit 6-Stunden-Intervall bedeutet 09:00, 15:00, 21:00 und 03:00. Standard ist täglich.

Ein fehlgeschlagener Selbsttest wird immer protokolliert und benachrichtigt. Ein erfolgreicher landet höchstens einmal täglich im Ereignisprotokoll (sowie bei Erholung nach einem Fehler), damit ein kurzes Intervall das Protokoll nicht zuschüttet. Im Akkubetrieb wird der Selbsttest komplett ausgelassen — im Ernstfall hat der Countdown Vorrang. Ein Neustart wiederholt einen Selbsttest nicht, der im aktuellen Zeitfenster bereits gelaufen ist.

Wem selbst diese eine Zeile pro Tag zu viel ist — etwa als alleiniger Administrator, der weiß, wann sich ein Token geändert hat —, wählt „Erfolgreiche Selbsttests ins Eventlog schreiben" ab. Es verschwindet nur die routinemäßige grüne Zeile: Die Prüfung läuft weiter im eingestellten Intervall, Fehler werden wie bisher protokolliert und gemeldet, das System-Journal zeichnet jeden Lauf auf, und das Ergebnis je Host im Dashboard bleibt unberührt. Die Cluster-Prüfung hängt an Zeitplan und Logzeile des Selbsttests, also verstummt auch das Cluster <Name>: ok je Cluster; jede Warnung zum Cluster wird wie bisher gemeldet. Zwei grüne Zeilen überleben den Schalter ebenfalls: ein selbst angestoßener Lauf und die Meldung, dass sich ein Fehler erholt hat.

Ein wöchentliches oder monatliches Intervall gibt es bewusst nicht. Der Selbsttest existiert, um eine Berechtigung zu finden, die seit dem letzten Stromausfall kaputtgegangen ist — ein geändertes Token, eine neue Firewall-Regel, eine getauschte USV-Netzwerkkarte —, und nichts davon hält sich an einen Zeitplan. Stört das Ereignisprotokoll, gehört die Zeile abgeschaltet, nicht die Prüfung; soll der Zustand aktiv überwacht werden, fragt das Monitoring-System /api/health ab (siehe Monitoring) — das deckt zusätzlich den Fall ab, dass die Appliance gar nicht mehr läuft.

Das Speichern der Einstellungen löst keinen Selbsttest aus — das ist Absicht, damit das Bearbeiten der Konfiguration nicht die Proxmox-API belastet. Nach dem Ändern eines Tokens oder dem Aktivieren der Cluster-Option führt „Selbsttest jetzt ausführen" im Dashboard die Prüfung sofort aus, statt auf das nächste Zeitfenster zu warten. Das Ergebnis landet dabei immer im Ereignisprotokoll — die Einmal-pro-Tag-Drosselung greift hier nicht —, und im Akkubetrieb wird die Ausführung abgelehnt.

Für Hosts, die als Cluster-Mitglied markiert sind, prüft der Selbsttest zusätzlich einmal den Cluster: Token-Rechte, Quorum, Ceph-Wartungsflags, HA-Armierungszustand und die Shutdown-Policy des Datacenters. Ein gesunder Cluster wird als „Cluster <Name>: ok" protokolliert, damit „geprüft und in Ordnung" von „gar nicht geprüft" unterscheidbar ist. Die Kehrseite: ohne gesetzten Cluster-Haken läuft nichts davon, und im Protokoll steht dann nur die schlichte Zeile je Host.

Das Ergebnis wird zusätzlich je Host festgehalten: die Host-Tabelle im Dashboard zeigt die Beanstandung in ihrer Fehlerspalte auch dann, wenn gar nichts heruntergefahren wurde, und /api/health zählt, wie viele Ziele zuletzt bestanden haben.

    image: ghcr.io/ffind-dev/pve-ups:latest
    container_name: pve-ups
    restart: unless-stopped
    ports: ["8080:8080"]

      - pve-ups-data:/var/lib/pve-usv  # events.db, history.db + Engine-Zustand
volumes:
  pve-ups-config:
  pve-ups-data:

Anschließend http://<docker-host>:8080 öffnen und denselben Wizard wie beim LXC durchlaufen. Konfiguration und Eventlog bleiben über die beiden eingebundenen Volumes erhalten, ein docker compose down verliert also nichts.

Da es im Image keinen privilegierten Begleitprozess (kein systemd) gibt, funktionieren dort zwei Dinge anders: Updates erfolgen durch ein neues Image-Tag und ein Neuerstellen des Containers (docker compose pull && docker compose up -d) statt über den In-App-Uploader, und NTP/Zeitzone liegen in der Verantwortung des Docker-Hosts/Orchestrators statt über den Wizard gesetzt zu werden — beide Bereiche sind im Webinterface ausgeblendet. Alles Weitere (USV-Abfrage, Proxmox-Shutdown, Schwellwerte, Webhook, Selbsttest) ist identisch.

TZ am Container setzen. Die Selbsttest-Startzeit gilt in der lokalen Zeit des Containers, und ohne TZ läuft der Container in UTC — im Docker-Modus lässt sich die Zeitzone nicht über das Webinterface setzen.
Liegt das eigene Netz innerhalb von 172.17.0.0/16 – 172.31.0.0/16, den Standard-Adresspool von Docker vor dem Start des Containers verschieben — Docker beansprucht diesen Bereich für seine Bridges, und der Container würde eine USV oder einen Proxmox-Host darin nicht mehr erreichen. In /etc/docker/daemon.json z.B. {"bip":"10.210.0.1/24","default-address-pools":[{"base":"10.211.0.0/16","size":24}]}, danach systemctl restart docker.

11 Fehlerbehebung

Ein Backup Server meldet „Authentication failed (token invalid?)"

Fast immer der falsche Typ am Host-Eintrag. Proxmox VE und Proxmox Backup Server nutzen unterschiedliche Token-Schemata, und PBS kennt das von PVE überhaupt nicht — die Anfrage wird also abgewiesen, bevor das Token auch nur betrachtet wird, ganz gleich wie gültig es ist. Typ auf Proxmox Backup Server stellen und erneut testen. Läuft der Test dann durch, warnt aber, dass Sys.PowerManagement nicht bestätigt werden konnte, fehlt die ACL am Benutzer, am Token oder an beidem — siehe Abschnitt 4. Auch prüfen, ob die API-URL Port 8007 nutzt.

Update bleibt in der Warteschlange

Bleibt ein hochgeladenes Update bei „⏳ In Warteschlange" stehen, ist der Queue-Drainer auf dieser Instanz nicht aktiv. Das passiert einmalig bei Boxen, die aus einer sehr alten Version aktualisiert wurden. Einmalig im Container ausführen (aktiviert den Dienst dauerhaft):

pct exec <CTID> -- systemctl start pve-usv-agent.service
# oder direkt im Container:
systemctl start pve-usv-agent.service

Cluster: brauche ich je Knoten ein eigenes Token?

Nein. Benutzer, API-Token und ACLs liegen auf Datacenter-Ebene (/etc/pve); ein einmal auf einem beliebigen Knoten angelegtes Token gilt deshalb für alle. Ein zweiter Durchlauf der Befehle aus Abschnitt 4 würde nur melden, dass es den Benutzer schon gibt. Jeden Knoten mit derselben Token-ID und demselben Secret eintragen, aber mit seiner eigenen API-URL.

USV nicht erreichbar / Alarm

Adresse, Zugangsdaten und die Firewall zwischen Appliance und USV-Quelle prüfen. Im Wizard zeigt „USV testen" die genaue Ursache — die Details je Objekt aufklappen, um zu sehen, welches Objekt warum scheitert (siehe USV-Quellen). Ein Kommunikationsverlust allein fährt nichts herunter (Fail-safe).

Eine Schwelle löst nie aus

Nicht jedes Gerät meldet jeden Wert. „USV testen" ausführen: Liefert das Gerät keine Restlaufzeit oder keinen Ladestand, sagt der Test das über der Objekttabelle — die zugehörige Schwelle ist dann dauerhaft wirkungslos. Stattdessen „Akkubetrieb länger als (s)" nutzen; dieser Zeitgeber läuft auf der eigenen Uhr der Appliance.

Bei einer SNMP-USV zusätzlich die Einstellung MIB prüfen. Viele Karten veröffentlichen über ihre Hersteller-MIB, was sie in RFC 1628 auslassen; Automatisch findet das von selbst, ein Blick lohnt also nur, wenn die MIB von Hand festgelegt wurde (siehe USV-Quellen).

Eine APC-USV funktioniert nicht / liefert nichts Brauchbares

Die Einstellung MIB auf Automatisch stehen lassen — die APC-PowerNet- MIB wird dann von selbst genutzt. Nötig ist sie, weil Schneider RFC 1628 nur auf der Network Management Card 2 (AP9630/AP9631/AP9635) ab Firmware sumx/sy v5.1.7 unterstützt, während die älteren NMC1-Karten (AP9617/AP9618/AP9619) sie gar nicht implementieren. „USV testen" zeigt, welche MIB genutzt wurde und welche Objekte jede von beiden beantwortet hat.

Eine CyberPower-USV meldet „keine Antwort", obwohl die Karte erreichbar ist

„USV testen" ausführen. Steht in der Zusammenfassung, dass die reguläre Abfrage keine Antwort bekam, die Werte einzeln aber antworten, kann die Karte keine Anfrage nach mehreren Werten auf einmal verarbeiten: die MIB auf CyberPower stellen, die Wert für Wert gelesen wird. Antwortet die Karte gar nicht, Community bzw. Zugangsdaten prüfen und ob SNMP auf der Karte für die IP der Appliance freigegeben ist.

NUT: „kennt keine USV mit diesem Namen" oder gar keine Antwort

Der USV-Name muss dem Abschnittsnamen in der ups.conf von upsd entsprechen; upsc -l <host> listet die gültigen Namen. Antwortet gar nichts, lauscht upsd meist nur auf localhost — seine LISTEN-Direktive muss die Schnittstelle abdecken, über die die Appliance verbindet, und TCP 3493 muss offen sein.

SNMPv3 mit Verschlüsselung schlägt fehl

Meldet ein authPriv-Benutzer „Ciphering services not available" oder weist der Test auf fehlende Verschlüsselung hin, fehlt der Appliance das Python-Paket cryptography, das die DES-/AES-Verfahren bereitstellt. Versionen bis einschließlich 3.0.0 haben es nicht mitinstalliert. Ein Update der Appliance behebt das — das Paket kommt automatisch mit. Zwei Dinge sind gut zu wissen: Es betrifft jedes Verschlüsselungsverfahren, ein Wechsel von DES auf AES hilft also nicht, und authNoPriv (Authentifizierung MD5/SHA, Verschlüsselung „none") funktioniert in der Zwischenzeit weiter, weil die Authentifizierung diese Verfahren nicht braucht.

Interne Namen: pve-usv

Der Produktname ist PVE-UPS, technisch heißen Dienst und Pfade aber weiterhin pve-usv — also z. B. systemctl status pve-usv, /etc/pve-usv/config.yaml und /var/lib/pve-usv/. Das ist beabsichtigt und hält Updates bestehender Installationen kompatibel.

12 Änderungsverlauf (Auszug)

Vereinfachte, nutzersichtbare Highlights. Der vollständige technische Verlauf steht im Changelog des GitHub-Repositories.

4.3.0 2026
  • Reiter „Verlauf": Restlaufzeit, Last und Ladung jeder USV im Zeitverlauf, mit Ausfällen, Auslösern und Markierungen aus dem Ereignisprotokoll, Zoom, frei wählbarem Zeitraum, Ausfall-Tabelle und CSV-Export. Nach einem Update bleibt er aus, bis Sie ihn unter Einstellungen → System einschalten — siehe Verlauf.
  • „Alle Gäste clusterweit zuerst stoppen" ohne Ceph: Vor dem ersten Knoten werden alle Gäste gleichzeitig zum Herunterfahren aufgefordert, statt Knoten für Knoten in Startreihenfolge — für Cluster, bei denen das länger dauert, als der Akku hält. Siehe den Gäste-Stopp.
  • CyberPower-Netzwerkkarten werden über ihre eigene MIB gelesen, auch Karten ohne RFC 1628. „Automatisch" scheitert über SNMP v2c nicht mehr an Karten, die ein fehlendes Objekt mit einem Fehler beantworten.
  • Das Docker-Image läuft auf einem Raspberry Pi (64- und 32-Bit).
4.2.0 2026
  • Ein abgeschalteter Webhook braucht keine URL mehr. Ein halb vorbereitetes Benachrichtigungsziel bleibt als Entwurf erhalten; nur ein aktives besteht weiterhin darauf, irgendwohin senden zu können.
  • Webhooks können zusätzliche Header mitschicken. Ziele, die mehr als einen brauchen — etwa Nextcloud Talk mit OCS-APIRequest und Accept neben der Authentifizierung —, funktionieren jetzt ohne vorgeschalteten Proxy.
  • Passwortmanager können die Anmeldemaske wieder ausfüllen. Die Anmeldeseite ist ein echtes Formular mit Benutzernamensfeld — daran hängt das automatische Ausfüllen; die Token- und Passwortfelder in den Einstellungen sind so gekennzeichnet, dass ein Manager sie in Ruhe lässt.
  • Erfolgreiche Selbsttests lassen sich aus dem Eventlog heraushalten, ohne die Berechtigungen seltener zu prüfen. Fehler, Erholungen und „Selbsttest jetzt ausführen" melden immer.
4.1.0 2026
  • Eine USV mit veraltetem „Zeit auf Akku“-Zähler löst keinen sofortigen Shutdown mehr aus. Die Appliance misst den Ausfall jetzt mit der eigenen Uhr, statt dem Zähler zu glauben, den die USV meldet — den der Standard nur für den Akkubetrieb festlegt und den etliche Karten aus dem letzten Ausfall behalten. Der laufende Timer übersteht einen Neustart des Dienstes.
  • Eine USV, die antwortet, ohne ihre Stromquelle zu nennen, ist ein Alarm und keine Entwarnung. Bei SNMP wie bei NUT löscht eine solche Messung mitten im Ausfall keinen laufenden Countdown mehr — und sie gilt auch nicht als Stille, „Shutdown bei reinem Kommunikationsverlust“ greift also nicht bei einem Gerät, das antwortet.
  • Ein fehlgeschlagener Shutdown wird wiederholt — drei Versuche statt einem, damit eine ausgelastete Proxmox-API oder eine abgebrochene Verbindung keine Maschine mehr laufen lässt, während das Dashboard sie als erledigt zeigt.
  • Ein Cluster nimmt nur die Knoten mit, die das auch wollten, und die drei Cluster-Schalter werden einmal je Cluster gelesen statt von dem Knoten, der zufällig zuerst auslöste. Siehe Abschnitt 6.
  • Außerdem: Webhook-Fehler werden gemeldet, statt unsichtbar zu scheitern, ein aktiver Testmodus sagt das auf dem Dashboard, Einträge, die ihre Aufgabe nicht erfüllen können (Host ohne Token, USV ohne Adresse), werden gekennzeichnet, und kein Geheimnis erreicht mehr den öffentlichen Status-Endpunkt.
4.0.0 2026
  • Proxmox-VE-Cluster werden vor dem Shutdown vorbereitet Beta. Wird ein Knoten als Cluster-Mitglied markiert, disarmt PVE-UPS einmal je Cluster den HA-Manager — und stoppt mit der Ceph-Option zuvor alle Gäste und setzt danach die Wartungsflags —, bevor der erste Knoten heruntergefahren wird. Die Schaltfläche „Cluster wiederherstellen“ im Dashboard macht das danach rückgängig. Setzt Proxmox VE 9.2 oder neuer voraus und ist durchgehend opt-in; siehe Abschnitt 6.
  • Ein Cluster wird als Einheit heruntergefahren (standardmäßig an): Ein fälliger Knoten nimmt den gesamten Cluster mit, in der konfigurierten Reihenfolge, statt einen halbierten Cluster mit disarmtem HA zurückzulassen. Abschaltbar.
  • Mehrere Webhooks statt nur einem, jeder mit eigenem Format, Filter und Test — dazu neue Formate für Slack, Discord und ntfy sowie eine eigene Vorlage. Siehe Abschnitt 9.
  • Der Selbsttest ist nützlicher geworden: Er läuft automatisch nach dem Wiederarmieren, „Selbsttest jetzt ausführen“ startet ihn sofort, und das Umbenennen eines Hosts verwirft sein API-Token nicht mehr. Siehe Abschnitt 4.
3.5.0 2026
  • Auch ein Proxmox Backup Server lässt sich jetzt herunterfahren. Jeder Host-Eintrag hat einen Typ — Proxmox VE oder Proxmox Backup Server —, der über Token-Schema und geprüftes Recht entscheidet. Ein PBS scheiterte bisher unabhängig vom Token immer als „ungültig"; die Einrichtung steht in Abschnitt 4, inklusive der Begründung, warum wir in Produktivumgebungen davon abraten, PBS an dieselbe Instanz zu hängen.
  • Beim Backup Server ist das Feld „Node" nur eine Bezeichnung. PBS ignoriert den Node-Namen im API-Pfad, dort muss also nichts zum Hostnamen passen.
  • Hosts werden jetzt in Stufen abgeschaltet statt strikt nacheinander: Einträge mit gleicher „Reihenfolge" werden gleichzeitig angewiesen, der eigene Host kommt weiterhin zuletzt, und jeder Befehl hat eine harte Obergrenze. Eine Maschine, die nicht mehr antwortet, kann die übrigen und den Akku-Countdown damit nicht mehr aufhalten — siehe Abschnitt 6. Der Wizard zeigt die daraus entstehende Abschaltfolge live unter der Host-Liste an, man sieht also, welche Hosts gemeinsam und welche danach drankommen.
  • Das Selbsttest-Ergebnis wird je Host gemerkt: ein kaputtes Token erscheint jetzt in der Host-Tabelle des Dashboards und in /api/health, nicht mehr nur im Ereignisprotokoll.
3.4.0 2026
  • Der Webhook spricht jetzt die Sprache seines Ziels: neben dem bisherigen Status-JSON kann er eine Microsoft-Teams-Karte oder einen kurzen Klartext-Status senden. Siehe Webhook-Benachrichtigungen.
  • Ein neuer Stufenfilter bestimmt, welche Ereignisse überhaupt gesendet werden. Standard ist Warnungen und Kritisches — reine Entwarnungen kommen also nicht mehr an; für das bisherige Verhalten die Stufe auf Alle Ereignisse stellen.
  • „Testbenachrichtigung senden" schickt eine Beispielmeldung mit den aktuell eingetragenen Werten — ohne vorher zu speichern — und meldet das HTTP-Ergebnis des Ziels.
  • Ein ausgeführter oder zurückgenommener Shutdown (shutdown sent / shutdown aborted) gilt als Warnung statt als Info und wird im Ereignisprotokoll gelb dargestellt.
3.3.0 2026
  • APC-USVs werden richtig unterstützt: Eine SNMP-USV lässt sich jetzt über eine Hersteller-MIB statt über RFC 1628 lesen, als erste APC PowerNet. Damit sind auch APC-Karten erfasst, die über RFC 1628 gar nicht erreichbar sind — die älteren NMC1 (AP9617/AP9618/AP9619) — sowie NMC2-Karten mit Firmware unter sumx/sy v5.1.7. Siehe USV-Quellen.
  • Die neue Einstellung MIB steht auf Automatisch und erfordert keine Aufmerksamkeit: Bestehende USV-Einträge erhalten sie beim Update, und eine USV wechselt von selbst auf ihre Hersteller-MIB, sobald sie darauf antwortet.
  • Karten, die beides beherrschen, liefern genauere Werte: PowerNet meldet die Restlaufzeit in Hundertstelsekunden statt in ganzen Minuten und kennzeichnet einen Selbsttest als solchen — RFC 1628 kann ihn nicht von einem echten Stromausfall unterscheiden.
  • Der USV-Test erklärt sich selbst: Im Modus Automatisch listet er beide MIBs auf und nennt, für welche er sich entschieden hat und warum. Das Dashboard zeigt die genutzte MIB an.
3.2.0 2026
  • USVs ohne Netzwerkkarte lassen sich jetzt überwachen: Ein USV-Eintrag wird entweder wie bisher per SNMP gelesen oder über einen NUT-Server — so werden USB- und seriell angeschlossene USVs erreicht. Beides ist in einer Instanz mischbar. Siehe USV-Quellen.
  • PVE-UPS bleibt ein strikt nur lesender NUT-Client — kein upsmon, keine Shutdown-Skripte, keine Konfigdateien. Die Entscheidung bleibt in der Appliance.
  • Der USV-Test benennt tote Schwellen: Meldet ein Gerät weder Restlaufzeit noch Ladestand, sagt der Test das — statt eine Schwelle zu hinterlassen, die stillschweigend nie auslöst.
  • Ein NUT-Server, der veraltete Daten liefert (sein Treiber ist abgestürzt), gilt als nicht erreichbar — Alarm, nie ein Shutdown, und nie mit „Netzbetrieb" verwechselt.
